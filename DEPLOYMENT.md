# Hostinger deployment

This repository is a Node.js monorepo with two separate Hostinger websites:

- `apps/web`: Next.js 16 frontend and server-rendered pages.
- `apps/api`: Express 5 API, Prisma 7, and a pooled MySQL connection.
- `packages/contracts`: shared TypeScript/Zod contracts built before either app.

Deploy the frontend and API as separate Hostinger Node.js websites. Use `apps/web` as the frontend root so Next.js starts from the directory containing its `.next` build; keep the API rooted at `./` for its workspace migration and build commands. No Docker, PM2, Nginx, Apache, or SSH command is required to start the managed Node.js apps.

## Runtime and project commands

- Recommended runtime: Node.js `22.12.x` (also supports Node.js `24.x`). `.nvmrc` selects `22.12.0`.
- Package manager: npm, using the root `package-lock.json` and npm workspaces.
- Install: `npm ci`.
- Full build: `npm run build`.
- Web build: `npm run build:hostinger:web`.
- API build: `npm run build:hostinger:api`.
- Web start: `npm start` (delegates to `@reviewroom/web`).
- API compiled entry: `apps/api/dist/server.js` (generated by the API build).

## Hostinger website settings

Create two Node.js websites from the same GitHub repository and branch. The frontend root is its app directory; the API root is the repository root. Hostinger output paths are relative to each selected root.

| Setting | Frontend: `ac108.rach-tours.com` | API: `api108.rach-tours.com` |
|---|---|---|
| Framework | Other | Other or Express.js |
| Root directory | `apps/web` | `./` |
| Node.js | `22.x` | `22.x` |
| Package manager | npm | npm |
| Build command | `npm run build:hostinger:web` | `npm run build:hostinger:api` |
| Output directory | `.next/hostinger` | `apps/api/dist` |
| Entry file | `.next/hostinger/server.js` | `apps/api/dist/server.js` |
| Start command, if Hostinger asks | Hostinger starts the entry file | Hostinger starts the entry file |

**Important:** use `apps/web` as the frontend root. Build Next.js in standalone mode, then package the standalone server, traced `node_modules`, shared workspace files, and static assets into `.next/hostinger`. Select Hostinger's `Other` preset for this frontend, use `.next/hostinger` as output directory, and set `.next/hostinger/server.js` as its entry file. This bypasses Hostinger's automatic Next.js runtime packaging, which omitted the React dependency. The API remains rooted at `./` because its migration and build commands use the repository workspace root.

Set `NPM_CONFIG_INCLUDE=dev` for both Hostinger websites if Hostinger installs with `NODE_ENV=production`. Build tools such as TypeScript and Tailwind CSS are development dependencies and must be present during the build. Never use `npm install --omit=dev` for these build steps.

## Environment variables

Enter these in each website’s Hostinger environment settings. Do not commit or upload `.env`, `.env.hostinger`, `.env.hostinger-web`, or `.env.hostinger-api`.

Frontend build/runtime:

| Name | Value |
|---|---|
| `NODE_ENV` | `production` |
| `API_INTERNAL_URL` | `https://api108.rach-tours.com` |
| `NPM_CONFIG_INCLUDE` | `dev` when production-mode installs omit development dependencies |
| `PORT` | Supplied by Hostinger; do not hard-code it |

API build/runtime:

| Name | Value |
|---|---|
| `NODE_ENV` | `production` |
| `HOST` | `0.0.0.0` (also the application default) |
| `PORT` | Supplied by Hostinger; the app uses it before its local `API_PORT` fallback |
| `DB_HOST` | Hostinger-provided database host |
| `DB_PORT` | Hostinger-provided database port (usually `3306`) |
| `DB_NAME` | Exact database name from Hostinger |
| `DB_USER` | Dedicated database user |
| `DB_PASSWORD` | Database user's password |
| `DB_SSL` | Optional; leave unset for Hostinger's loopback database. Remote production databases require verified TLS by default; set `true` to explicitly enable verified TLS or `false` only when the remote database's network path is otherwise protected. |
| `DATABASE_CONNECTION_LIMIT` | Start at `5`; ensure instance count × pool size stays below the database connection limit with operating headroom |
| `SESSION_SECRET` | Unique random value, at least 32 characters |
| `TOKEN_ENCRYPTION_KEY` | Unique 32 random bytes encoded as base64url; back up securely because changing it prevents revealing existing encrypted links |
| `WEB_ORIGIN` | `https://ac108.rach-tours.com` (origin only, no path or trailing slash) |
| `TRUSTED_PROXIES` | Leave empty unless you know the exact trusted proxy address/CIDR |
| `NPM_CONFIG_INCLUDE` | `dev` when production-mode installs omit development dependencies |
| `BOOTSTRAP_OWNER_ON_DEPLOY` and five `BOOTSTRAP_*` values | First deployment only; set for a fresh database, then remove immediately |

`PORT` is injected by Hostinger. Do not set it to a fixed value. The API retains `API_PORT=4000` as a local fallback. `DATABASE_URL` is still accepted for existing installations, but new setup should use all five `DB_*` values. The Prisma migration config derives its URL from those values.

The root `.env.example` contains safe local placeholders and all application settings. Copy it to `.env` for local work, then replace the placeholders. Production secrets belong only in Hostinger's environment-variable manager.

## Database setup and release order

1. Create the MySQL database and a dedicated least-privilege application user in Hostinger. Use the exact connection details Hostinger displays; do not enable public remote database access unless the hosting topology requires it.
2. Add the five `DB_*` values to the API website environment so both Prisma migrations and the API can connect.
3. Back up the database before a release that applies migrations. Hostinger's API build command runs `prisma migrate deploy` before compiling; keep schema migrations compatible with the currently running app during rollout.
4. Existing databases run a read-only assignment integrity preflight before migrations. If it reports orphaned or cross-organization assignments, the build stops before changing the schema. Review the reported IDs and repair deliberately with a backup; the migration never deletes or rewrites assignment data to make a constraint pass.
5. The assignment migration adds an assignment update version and same-organization foreign keys. Existing assignment and submission records are retained.
6. For a new, empty database only, keep the API build command as `npm run build:hostinger:api`. Temporarily set `BOOTSTRAP_OWNER_ON_DEPLOY=true` and all five `BOOTSTRAP_*` values (`BOOTSTRAP_EMAIL`, `BOOTSTRAP_NAME`, `BOOTSTRAP_PASSWORD`, `BOOTSTRAP_ORGANIZATION`, `BOOTSTRAP_SLUG`) in the API environment, then deploy once. The build script applies migrations, creates the owner, and builds the API. After a successful deployment, immediately remove the flag and all five bootstrap variables. Never rerun bootstrap on an existing installation.
7. Deploy the API first, confirm it is healthy, then deploy/rebuild the frontend so its `API_INTERNAL_URL` rewrite is included.
8. Verify login, reviewer access scoping, public review submission, form publishing, and database readiness on the deployed domains before sharing links. Then sign in as an administrator and verify assignment search, assign, reassign, unassign, and reviewer access against the deployed API.

## Health and existing API routes

- `GET /health` returns HTTP 200 and `{"status":"ok"}` without requiring a database round trip; use it for process liveness.
- `GET /api/v1/health/live` is the existing API liveness endpoint.
- `GET /api/v1/health/ready` runs a database readiness query; a failure is logged without returning credentials or raw SQL errors.
- Existing API route groups: `/api/v1/auth`, `/forms`, `/progress`, `/members`, `/review-links`, `/public/review`, `/review-targets`, `/submissions`, `/audit-events`, and `/organization`.

Test the deployed health endpoint with a browser or:

```text
https://api108.rach-tours.com/health
```

It should respond with status `200` and JSON `{"status":"ok"}`. Then check `/api/v1/health/ready` to confirm MySQL connectivity.

## Platform boundaries and capacity

Local URLs in `.env.example`, `next.config.ts`, and the load-smoke script are development/test defaults. Set `API_INTERNAL_URL` and `WEB_ORIGIN` to production HTTPS origins in Hostinger. The production app does not depend on Docker, PM2, Nginx, Apache, Redis, or manually started SSH processes. Static Next.js assets are cacheable; authenticated HTML and API data are marked non-cacheable.

Hostinger managed Node.js has plan-specific process/memory limits, request timeouts, and app-slot counts. This repository's existing in-memory API rate limits are per process, so use the Hostinger edge/WAF for shared limits if adding replicas. A successful build and local start do not prove arbitrary high-traffic capacity; measure the exact plan and MySQL quota under representative load before making capacity claims.
